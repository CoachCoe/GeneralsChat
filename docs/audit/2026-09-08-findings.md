# Blockers

## B1 — A classification the model returned unparseably is written as a real classification, with two invented 24-hour obligations
**SPEC-53, FLOW-51.** `src/lib/ai/claude-service.ts:516-545` (catch at `:525`,
default at `:534-544`)

The FLOW-35 fix was applied one layer too high. `IncidentClassifier` throws
`ClassificationUnavailableError` and `getDefaultClassification` was correctly
deleted, with `src/lib/ai/classifier.ts:122-128` recording why: *"a
plausible-looking safe default is exactly what someone would re-wire."* But the
inner call still swallows. The model call sits **outside** the `try`
(`:506-514`); the `try` at `:516` wraps only the parse, and its catch returns:

```
534  type: 'other',
535  severity: 'medium',
537  reasoning: 'Unable to automatically classify. Manual review required.',
538  requiredActions: [
539    { description: 'Review incident details', dueInHours: 24 },
540    { description: 'Contact administrator', dueInHours: 24 },
541  ],
```

So a malformed or schema-invalid response — the exact case the zod schema was
added for (SEC-9) — never reaches the classifier's catch. The route writes
`incidentType: 'other'`, `severity: 'medium'` permanently
(`src/app/api/chat/route.ts:156-168`, gated on `!incident.incidentType` at
`:141`, so there is no retry and no endpoint to correct it), and
`createObligations` writes those two invented 24-hour obligations whenever the
second pass returns nothing (`route.ts:327-338`).

Only an *upstream* failure behaves as `docs/roadmap.md` claims. The record
produced is indistinguishable from a genuine "we could not tell" — on the
incident where the system knew least — which is precisely the defect FLOW-35
exists to prevent.

**Fix.** Delete the default; rethrow after the existing `logError` so
`IncidentClassifier` wraps it and the FLOW-35 path in the route takes over
unchanged. Unit-test that a non-JSON and a schema-invalid response both throw.

## B2 — Classification is committed before obligations are derived, so a failure between the two leaves a classified incident with no obligations, permanently
**MT-2, FLOW-52.** `src/app/api/chat/route.ts:141` (retry gate), `:156-168`
(incident committed), `:192-205` (retrieval), `:209-211` (obligations),
`src/lib/ai/claude-service.ts:640` (the unguarded call inside
`deriveObligations`)

On the first substantive turn the route classifies, **writes `incidentType`**,
retrieves, and only then derives and writes obligations. `deriveObligations`
guards its JSON parse (`claude-service.ts:646-657`) but not the model call at
`:640`. A timeout, a 429, a 5xx, or the "returned no text content" throw at
`:391-395` is wrapped into a plain `Error` at `:417` and propagates out of the
route body — and because it is not an `LLMUnavailableError` it misses the 503
branch at `route.ts:255-261` and returns a generic 500.

The incident update has already committed. So on the next turn
`!incident.incidentType` is false, `classification` stays `null`, and the
`if (classification)` guard at `:209` means `createObligations` is never called
again. `complianceAction.create` appears nowhere else in the tree, so nothing
will ever retry.

The incident is left classified, with a severity and a timeline, and with **zero
`ComplianceAction` rows**. It is worse than FLOW-35 in one respect: an
unclassified incident is visibly unclassified and retries, whereas this one looks
complete. An administrator sees a classified `abuse_neglect` incident with an
empty obligation queue and no warning, which reads as "nothing is required of
you". `docs/roadmap.md` OQ-5 names this outcome directly: *"*nothing* is how a
mandated report gets missed."*

A contributing cause: there is no `$transaction` anywhere in the codebase
(`grep -rn '\$transaction' src/ scripts/` returns nothing), so the two writes
are independent with a failure window between them.

**Fix.** Do not let the retry gate depend on a field written before the
obligations exist. Wrap the classification write and `createObligations` in one
`prisma.$transaction` so a phase-two failure rolls back the `incidentType` stamp
and the next turn retries the whole thing — matching the FLOW-35 reasoning.

## B3 — An unverified obligation that is overdue or due today is rendered in no group at all
**SPEC-51, TEST-51, FLOW-68.** `src/app/page.tsx:72-78` (the filters), rendered
`:153-159`

The three groups do not partition the open set:

```
72  const verified = open.filter(o => o.deadlineSource !== 'model');
74  const overdue = verified.filter(o => due(o) !== null && due(o)! < now);
75  const today   = verified.filter(o => due(o) !== null && due(o)! >= now && due(o)! <= endOfToday);
78  const later   = open.filter(o => due(o) === null || due(o)! > endOfToday);
```

`overdue` and `today` are drawn from `verified`; `later` requires a deadline
after midnight tonight or none at all. **A model-sourced obligation whose
deadline is in the past or later today satisfies none of the three**, so it is
rendered nowhere and cannot be marked done.

`deadlineSource` defaults to `"model"` in the schema
(`prisma/schema.prisma:149`), and with a thin library that is the common case —
the roadmap says so explicitly. The row that disappears is the urgent one. A
24-hour DCYF report derived without a citable provision vanishes from the queue
an administrator opens *to find out what they are late on*.

The code's own comment two lines above promises the opposite: *"Those obligations
are still listed below, and say on their own row that they need confirming."*
And the subhead still counts them — the page can say *"3 obligations have a
deadline no loaded policy states"* above a queue that shows none of them. The
e2e fixture already seeds such a row (`e2e/support/seed.ts:190-196`), so it is
invisible in the suite today; no test asserts the queue is exhaustive.

**Fix.** Partition `open` completely. Keep `overdue`/`today` (verified-only)
driving the headline and tallies, per OQ-5, and add a fourth group for
model-sourced obligations due by tonight, rendered in a neutral tone so the
no-red/amber rule still holds. Every open obligation then falls in exactly one
of four groups. Add a test asserting the rendered queue count equals the open
count. See **OQ-7** for the group's name and placement.

## B4 — The headline asserts "You're clear." before the data has loaded and after the load has failed
**FLOW-69.** `src/app/page.tsx:60-101` (computed unconditionally), `:115-123`
(rendered unconditionally), `:28` (`loading` starts `true`), `:26`
(`obligations` starts `[]`)

`headline` and `subhead` are derived from `open.length`, which is `0` before the
first fetch resolves and `0` again if it fails. Both are rendered
unconditionally in 40px serif; only the `StateBlock`s below them are gated on
`loading` / `error` (`:140-144`). So the page opens by stating

> **You're clear.** No obligations are outstanding.

and says the same thing permanently after a failed fetch — including the 401 an
administrator gets from the idle session timeout, where the error block reads
"Could not load your obligations" *underneath* a 40px serif claim that nothing
is outstanding.

This is the product's single most prominent sentence, it is a claim about legal
exposure, and it is asserted from an empty array. `CLAUDE.md`: *"a confidently
wrong statutory deadline is worse than no answer. When in doubt, say the system
does not know."*

**Fix.** Suppress the headline and subhead while `loading` or `error` is set,
and render a neutral placeholder in their place. Add an e2e assertion that the
"You're clear." copy is absent when `/api/obligations` returns a failure.

## B5 — An unverified deadline is painted red and amber, and counted in the "N overdue" chip
**DEAD-81, TEST-54, SPEC-52, FLOW-61.** `src/app/incidents/[id]/page.tsx:182`
(the count), `:233-237` (the red pill), `:380` (the tinted stamp), `:406-413`
and `:440-445` (timeline dot and meta); `src/app/incidents/page.tsx:182-184`,
`:198` (list countdown)

OQ-5, shipped and recorded in `docs/roadmap.md`: **"A model-sourced deadline gets
no red or amber countdown"**, and the lateness headline *"counts only
policy-backed ones… it is the number in the product that most looks like fact."*

`DeadlineClock` implements this correctly — it takes a `verified` prop and falls
back to `text-text-tertiary` (`DeadlineClock.tsx:38`), and `ObligationRow` passes
it (`:64`). **Every other surface that renders a deadline ignores provenance.**
`src/app/incidents/[id]/page.tsx:182` computes overdue with a raw
`new Date(a.dueDate).getTime() < Date.now()` over *all* open actions, and that
count drives a red-bordered "{n} overdue" pill and tints the `Obligations` stamp
bar. `src/app/incidents/page.tsx:198` paints the soonest deadline
`DEADLINE_COLOR[deadline.state]`.

So the same row reads two ways on the same screen, 35 lines apart: a dimmed,
hedged countdown in the obligation list, and a red "3h late" pill in the header
above it. The red one is the statutory-lateness claim, and it is being made for a
deadline the system cannot substantiate.

Two contributing causes worth fixing with it: the page-level `Action` interface
omits `deadlineSource` and the row is cast `as Obligation` at `:330`, so the
compiler cannot see the field the count should filter on; and "is this overdue?"
now has four implementations (DEAD-81), of which only one consults provenance.
The timeline rung at `:411-412` is doubly wrong — amber for *any* non-overdue
open obligation regardless of what `describeDeadline` returned.

**Fix.** Put the rule in one place: a helper beside `DEADLINE_COLOR` in
`src/lib/deadline.ts` that takes the state and the provenance and returns the
token, with a unit test. Thread `deadlineSource` through both page-level
interfaces (both endpoints already return it —
`src/app/api/obligations/route.ts:52` and the `complianceActions` include at
`src/app/api/incidents/[id]/route.ts:47-49`), drop the `as Obligation` cast, and
filter the `:182` count the way `src/app/page.tsx:72` does. See **OQ-6** on
whether the rule is meant to reach every surface.

## B6 — The `dueInHours → dueDate` conversion is pinned by no test: every statutory clock can be wrong by 60× with a green suite
**TEST-49.** `src/lib/ai/classifier.ts:58`, `src/app/api/chat/route.ts:318`

```
58   dueDate: new Date(Date.now() + action.dueInHours * 60 * 60 * 1000),
318  dueDate: new Date(Date.now() + obligation.dueInHours * 60 * 60 * 1000),
```

This arithmetic is the product. It converts the model's `dueInHours` into the
`dueDate` every countdown, every "N overdue" count and every red chip is
computed from. Change either `* 60 * 60 * 1000` to `* 60 * 1000` and all 151
unit tests and all 59 e2e tests still pass: a 24-hour mandatory-report clock
becomes 24 minutes, and the suite says nothing.

Verified: `grep -rn "dueDate|dueInHours" e2e/ src/**/*.test.ts` returns only
`e2e/support/seed.ts:195,202,235`, which set `dueDate` **directly** as fixture
values, and `e2e/support/claude-stub.ts:30-31,71-74`, which supply `dueInHours`
into the stub with nothing asserting the resulting date. Nothing reads a
`dueDate` produced from a `dueInHours` anywhere in either suite.

OQ-5 gave this expression a second copy, so it is now unpinned in two places
that must agree. Prior TEST-24, still open.

**Fix.** Extract the conversion into one exported function in
`src/lib/deadline.ts` — `dueDateFromHours(hours, now)` — use it at both sites,
and unit-test it against known values (24 → +24h, 240 → +10d, 0, fractional).
Add one e2e assertion that a stubbed `dueInHours: 24` produces a deadline the UI
renders inside the next day.

## B7 — `scripts/clear-incidents.ts` deletes every incident record and the audit log from whatever `.env` points at, with no guard of any kind
**DEAD-90, DOC-24, REPO-23.** `scripts/clear-incidents.ts:1-32`

Filed as major by two passes; **promoted to blocker here.** The reasoning: the
artefact itself is the hazard, the target is production by default, and what it
destroys is the record of incident reports about minors plus the accountability
trail over them.

```
 1  import { prisma } from '../src/lib/db';
 9  await prisma.auditLog.deleteMany({});
12  await prisma.complianceAction.deleteMany({});
15  await prisma.attachment.deleteMany({});
18  await prisma.conversation.deleteMany({});
21  const result = await prisma.incident.deleteMany({});
```

Five unfiltered `deleteMany({})`. No dry run, no confirmation prompt, no
`--apply` flag, and **no database-name guard** — unlike `e2e/global-setup.ts:19-30`,
which refuses any database whose name lacks `test` precisely so that "a mistyped
`DATABASE_URL` cannot wipe real data". It imports `prisma` from `src/lib/db`, so
it resolves `DATABASE_URL` from `.env`, which `CLAUDE.md` states points at the
hosted Postgres the pilot runs on. It is not wired into `package.json`, so it
leaves no trace in the script list a maintainer would scan, and `CLAUDE.md`'s
warning list — which names `policies:*`, `prisma`, `scripts/test-phase3.ts` and
`scripts/test-rag.ts` — **omits it**, reading as exhaustive while missing the
worst one.

It also deletes `auditLog` first. That table is the only record of who read which
student's incident, so a single unguarded run destroys both the reports and the
evidence of access to them.

**Fix.** Add the `e2e/global-setup.ts` database-name guard and require an
explicit `--apply` flag, defaulting to a dry run that prints the counts it would
delete — the pattern `policies:reindex` already establishes. Add it to
`CLAUDE.md`'s warning list, and wire it into `package.json` so it is visible.

## B8 — `scripts/test-rag.ts` inserts an active district *bullying* policy into whatever `.env` points at
**TEST-63.** `scripts/test-rag.ts:110-119`, then `:125-129`

Filed as major; **promoted to blocker here**, because of what it collides with.

```
110  const policy = await prisma.policy.create({
112    title: 'School Bullying Prevention Policy',
113    content: samplePolicyContent,
114    jurisdiction: 'district',
115    category: 'bullying',
117    isActive: true,
```

Synthetic policy text, marked `isActive: true`, `jurisdiction: 'district'`,
`category: 'bullying'`, then indexed into the vector store. No
database-name guard; `DATABASE_URL` comes from `.env`.

Bullying is the pilot's **only fully covered subject** (`docs/roadmap.md`: the
real Policy JICK and the SAU 24 investigation form, 11 chunks). And the roadmap
records that the previous synthetic bullying policy was deactivated for exactly
this reason: *"Its own text calls it `Policy Number: DISC-001`, a code that does
not exist — it was synthetic sample data, and it would have competed with the
real JICK for every bullying query."* Running this script re-creates that
situation, against production, in one command — and a mid-run failure leaves it
behind.

`CLAUDE.md` does warn about this file by name, which is why the passes graded it
major. It is promoted because the hazard is not "writes test rows" but "silently
degrades the guidance quality of the one subject the pilot can actually answer",
and the fix is three lines.

**Fix.** Give every `scripts/test-*.ts` the same `/test/i` `DATABASE_URL` guard
as `e2e/global-setup.ts`, refusing to run otherwise. These files are not part of
any gate, so the guard cannot break CI.

## B9 — `reuseExistingServer: false` does not stop the suite running against a foreign server, which is the production-write scenario its own comment describes
**MT-1.** `playwright.config.ts:52-62`, `e2e/global-setup.ts:19-30`

**Reproduced, not theorised.** An unrelated local Next app was listening on port
3100. `npm run test:e2e` then produced: the `webServer` command's own listen
failing (Playwright printed the bare error object, `address: '::', port: 3100`)
with **no** `EADDRINUSE` abort; Playwright's readiness probe against
`url: BASE_URL` satisfied by the foreign process, so the run proceeded as if the
server were ours; and `e2e/auth.setup.ts:12` navigating to the **foreign
application's** `/login`. The captured snapshot in
`test-results/auth.setup.ts-authenticate-as-admin-setup/error-context.md` is a
different product's sign-in page, showing our seeded credential
`e2e-admin@example.test` rejected with "Invalid email or password".

`reuseExistingServer: false` only governs whether Playwright *skips starting* its
own server. It does not assert the port is free, and the readiness probe accepts
any process that answers — so a server Playwright did not start is used anyway.
The config comment at `:55-60` says this is the thing it prevents:

> "reusing one already on this port silently discards ANTHROPIC_BASE_URL and runs
> the whole suite against the real API and whatever DATABASE_URL that process was
> given -- and .env points at production. global-setup guards the database it
> resets; it cannot guard a server it did not start."

This run failed loudly only because the squatter was a different product. The
dangerous case is the same app: `npm run dev` on port 3100 in another terminal is
this application with `.env`, i.e. the hosted pilot Postgres and the real
Anthropic API. The suite would then drive production in a browser while
`resetDatabase()` truncated the test database.

**Fix.** Preflight the port in `e2e/global-setup.ts` — it runs *before*
`webServer`, so it is the only place that can refuse before anything binds — and
point `webServer.url` at `${BASE_URL}/api/health`
(`src/app/api/health/route.ts:19-21`) so the probe is at least app-specific.

## B10 — Attachments have zero coverage of any kind, against an explicit invariant
**TEST-53.** No `Attachment` row is created in `e2e/support/seed.ts` or any spec

`CLAUDE.md` names this an invariant: *"**Attachments are student records.** They
live outside `public/` and are served only through `GET /api/attachments/[id]`,
which re-checks session and ownership. Never reintroduce a direct file URL."*

The implementation is correct — the security and journey passes both traced it
clean. It is also entirely untested. No test creates an `Attachment`, so the
ownership check (`src/app/api/attachments/[id]/route.ts:36-43`), the
404-not-403 response, the path-containment assertion (`:50`), and the
`nosniff` / `private, no-store` / `application/octet-stream` headers (`:64-72`)
are all unexercised. Deleting the ownership check would leave the suite green.

Prior TEST-30, still open.

**Fix.** Seed one attachment owned by each of the two users, and add specs for:
the owner downloads it; the other reporter gets 404; the response carries the
three headers; and the stored path is not a URL under `public/`.

## B11 — `incidentScope` has a falsifiable test on four of eight scoped lookups
**TEST-52.** Covered: `src/app/api/incidents/[id]/route.ts:32`, `:110`,
`src/app/api/obligations/[id]/route.ts:38`, `src/lib/ai/incident-summary.ts:37`.
Uncovered: `src/app/api/chat/route.ts:55`,
`src/app/api/chat/[incidentId]/route.ts:19`, `src/app/api/chat/summary/route.ts`,
`src/app/api/attachments/upload/route.ts:51`

The 2026-09-01 audit found that the cross-user tests used ids that do not exist,
so deleting `incidentScope` left the suite green — *"SEC-7 with a passing test"*.
That fix genuinely holds for four call sites: `e2e/incident-management.spec.ts`
now uses real foreign ids read from the seed file, verified by both this pass and
the security pass.

The other four have no foreign-id test. Two of them are the worst ones to leave
uncovered: `GET /api/chat/[incidentId]` returns **a whole conversation
transcript**, and `POST /api/chat` accepts an `incidentId` and would append to
another reporter's incident. Deleting `...incidentScope(guard.user)` from either
line leaves all 210 tests passing.

**Fix.** Extend `e2e/incident-management.spec.ts` with a foreign-id case for each
of the four, using the seeded other-user incident id, asserting 404. Confirm each
fails with the scope removed.

## B12 — Nothing in the fixture is ever overdue *and* policy-backed, so the app's only red signal and its headline count are dead in test
**TEST-50.** `e2e/support/seed.ts:190-196`, `:198-204`, `:230-238`

Both seeded obligations are created with `deadlineSource: 'model'`, and every
obligation the chat flow creates during a run is in the future. Since the home
tallies and the headline count only policy-backed rows
(`src/app/api/obligations/route.ts:69-89`, `src/app/page.tsx:72-74`),
`counts.overdue`, `counts.today` and the entire `Overdue` group are **always
zero** in the suite.

So inverting the comparison at `src/app/page.tsx:74`, or dropping the `backed`
filter from the tallies, is invisible. The one number the product exists to
produce — "N things are late" — has no test that can see it be wrong. It is also
why B3 went unnoticed.

Prior TEST-31, still open.

**Fix.** Seed a third obligation that is `deadlineSource: 'policy'`, past due,
with a `policyId` and `citation`, and assert: the headline reads "One thing is
late.", `counts.overdue` is 1, and the row appears under `Overdue` with a red
countdown. That fixture is also what B3, B5 and B6 need.

# Open questions

Recorded rather than guessed, per the audit's own rule. Three passes numbered
theirs independently and collided; they are renumbered here into one sequence
continuing from OQ-5. Two near-duplicates were merged into **OQ-7**.

**OQ-6 — does the "no red or amber for a model-sourced deadline" rule apply to
every surface, or only the home page?** OQ-5 names two things: the countdown, and
*"the home page's 'N things are late'"*. The incident detail page has its own
count-of-lateness and tinted stamp, and the incidents list has its own countdown.
**B5** assumes the rule is about the class of signal and so covers all of them,
but the decision as written could be read as scoped to the home headline. A
per-surface reading would need saying, because it means the same row reads two
different ways on two pages.

**OQ-7 — where does an unverified obligation whose model deadline has already
passed belong in the home queue, and does it get its own group?** OQ-5 requires
it to be listed and to keep its urgency but forbids the red Overdue treatment.
The three current groups are all deadline-state labels, so none has an honest
heading for such a row. Options: put it in the time-correct group with a neutral
tone; give it a fourth "Needs confirming" group; or sort it into Later regardless
of date. These are different products. Note the status quo — rendered nowhere —
is not one of the options (**B3**).

**OQ-8 — how many policy categories are there?** `CLAUDE.md` says *"20 values"*;
`POLICY_CATEGORIES` has 21 entries (20 subjects plus `other`), and
`POLICY_MAPPING.md` groups exactly 20 subjects. Trivial in effect, but it is the
kind of number that gets asserted in a test.

**OQ-9 — is "any Azure service" an acceptable perimeter for the database holding
every incident record about a minor?** `--public-access 0.0.0.0` (SEC-34) admits
any Azure tenant's compute, not just this subscription's. Tightening it means
choosing between a VNet-integrated deployment and an IP allowlist, which is an
infrastructure decision.

**OQ-10 — who is allowed to be a policy source?** The DNS-rebinding gap (SEC-4)
is recorded in the roadmap as needing "a hostname allowlist, which is a decision
about permitted policy sources". SEC-32 narrows but does not close it. The
decision is still owed.

**OQ-11 — should the app refuse to start on a placeholder or weak
`AUTH_SECRET`?** Failing closed protects a real deployment and breaks any
scripted environment that supplies a dummy; the tradeoff is a product call.

**OQ-12 — what should closing an incident do to its open obligations?**
Today they stay open, counted and accruing lateness (FLOW-66). Cascading them to
a terminal state loses the record that they were never done; leaving them means
the queue counts obligations for closed incidents. Neither is obviously right.

**OQ-13 — should an incident's classification be correctable?** The roadmap lists
"Change classification" under *Deliberately not doing* ("No endpoint"), but
**B1** and **B2** both produce records only a correction endpoint can repair. The
question is whether the answer to a bad stamp is a correction path or making the
stamp impossible.

**OQ-14 — is `.doc` a supported policy format?** The upload surface accepts it
and the processor reads it as UTF-8 (FLOW-72), which turns binary into retrievable
policy text cited under a real policy's title. Rejecting it is the safe fix;
supporting it properly needs a converter.
